## Deployment boundary

The application uses one Node process with one persistent SQLite database. The repository has no Railway deployment-as-code configuration; the actual project, environment, service, attached volume, mount path, replica setting, command overrides, domains and variable presence must be verified in Railway by an authorized operator. Record identifiers and evidence privately, without secret values. The release must use a reviewed source revision and lockfile, not this dirty worktree.

Railway mounts a volume only when the service starts, **not** during build or pre-deploy. Therefore do not put `prisma migrate deploy`, `backup:sqlite`, a seed or any SQLite/file operation in Railway's pre-deploy command for this volume. Do not run migration implicitly on application startup either. The operator must approve a controlled maintenance window, stop traffic/writers and processors, take a consistent snapshot, and use an explicitly authorized runtime/maintenance procedure with the correct mounted volume and release image. The procedure, permissions, possible downtime and old/new artifact compatibility need a rehearsal before production. Railway's volume-backed service cannot use replicas and redeployment can entail a brief outage; do not promise zero downtime. See [Railway volumes](https://docs.railway.com/volumes/reference) and [pre-deploy commands](https://docs.railway.com/deployments/pre-deploy-command).
