# SIA Architecture

## MAXSPACE Identity

SIA remains the same shared Virtual CEO under MAXSPACE GROUP / MAXSPACE OS. The Boss Panel links to existing scoped tools and governed context; no new SIA, seeded agent authority, provider or autonomous executor is introduced. Stable legacy identifiers and historical phase descriptions remain preserved. See MAXSPACE_GROUP_ARCHITECTURE.md.

## F06 Scope-First Context

Current context authority is resolved from bounded selected principal relations and grant-root/requested-scope hierarchy reads, not a global organization dump. get_tasks now has a narrow source projection: current user/agent task and executive intersection, only related readable organization/project endpoints, plus existing reviewed source-authorized memory. It does not load the complete executive portfolio/Business Graph. Other registered read tools retain their authorized executive/graph contract with bounded primary and collection-wide nested reads. Output/final-memory byte limits and decision-history disclosure remain. Initial/final current authorization is reloaded; only structural paths, capability-ID projections and identical scope checks within one read are reused. No cross-request cache, provider integration, new authority or timeout padding is introduced. The F06 remediation report supersedes earlier global-hierarchy/include findings for the repaired paths; production load/SLO/token-cost acceptance remains NOT VERIFIED.

## Remediation Wave 03 Context Projection

The shared context contract and human/agent intersection are preserved. get_tasks consumes the executive dashboard's opt-in authorized task source collection. Decision memory retains its canonical payload and projects only the latest50 history entries, deterministic chronological display, explicit historyTruncated/historyLimit and response limitation; earlier history remains in the authorized executive record. Only history data is reused within one retrieval; canonical source/authority is re-read per reference. No cross-request authority cache is introduced. Incremental memory and final serialized response reject >1MiB explicitly instead of silently dropping decision context. Full source/query/bounds inventory and remaining principal/include/materialization cost findings are in `docs/audit/SIA_CONTEXT_COST_REVIEW.md`. Token/cost and production capacity remain NOT VERIFIED. No new tool/provider or autonomous authority is enabled.

## Phase 10 Security Review

SIA remains a scoped non-human tool consumer, not SQL/file/credential/external API authority. Memory queries are scope/expiry bounded before paging, then source-authorized before the visible 100-item limit. Human/agent intersection is unchanged; agent project candidate lookup is batched rather than repeated per capability. HTTP SIA mutations additionally have durable user budgets. Independent approval, explicit confirmation, immutable registered risk, current tool/grant revalidation and no autonomous high-impact execution remain mandatory. No enabled tools or agent grants are seeded. See PHASE_10_VALIDATION.md.

## Phase 09 Communication Gateway

The existing registry and scoped agent roles gain controlled send_email/send_whatsapp preparation contracts, not unrestricted API access. Message + immutable SIA_PROPOSAL carries external-action provenance and reuses current approval authority. Human-confirmed outbox processing revalidates both creator and agent authority, policy and consent; generic SIA execution stays disabled for these tools. Provider body text remains DATA and never invokes SIA. See COMMUNICATIONS_INTEGRATIONS.md.

## Phase 08 Virtual CEO

Phase 08 extends the existing SIA identity, scoped AGENT roles, tools, context and approval foundation. Controlled context is assembled using the current human/agent permission intersection before domain aggregation. Governed memory, immutable registry contracts, deterministic provider routing, concise evidence-based recommendations, private request/usage provenance and the protected /app/sia interface are implemented. The general executionEnabled=false gate remains; only create_task has a separate independent-human-approved, explicitly confirmed, transactionally verified gateway. High-impact autonomous execution is DISABLED. Earlier phase sections below describe historical boundaries; SIA_VIRTUAL_CEO.md is authoritative for current Phase 08 behavior.

## Phase 07 Deterministic Executive Context

Authorized metrics, explainable signals, attention handling, human decisions, changes, real observation trends, risk/opportunity records and briefing are future context only. No model/API integration, reasoning, memory, autonomous action or tool execution is installed. Any future SIA consumer must use the same source-aware authorization boundary; human decisions are not execution authority. The Phase 05 executionEnabled=false gate remains unchanged. See EXECUTIVE_INTELLIGENCE.md.

## Phase 06 Company Context

AIRA divisions, programs, batches, locations, responsibilities and shared execution/workflow relations are additional authorized business context only. SIA remains the existing non-human shared Virtual CEO identity and its canonical AGENT designation. No agent permissions/tools are seeded, no intelligence engine or company-specific autonomous executor is introduced, and Phase 05 executionEnabled=false remains enforced. See AIRA_COMPANY_OS.md.

## Phase 05 Approval Boundary

SIA_PROPOSAL requests bind an existing identity and registered action to a real resource, immutable policy and independent human approval chain. Preparation requires scoped human authority; decisions require sia.approve_action plus assigned approval/policy capabilities. siaBoundary checks current human approval and agent tool capability/allowlist, but always returns executionEnabled=false and verificationStatus=NOT_RUN. No autonomous executor or intelligence engine exists. Future controlled execution must reauthorize the exact proposal/version, verify its result and audit the complete execution. See OPERATIONS_MODEL.md.

## Phase 04 Execution Context

Projects, milestones, tasks, dependencies, goal hierarchy/progress provenance, blockers and deadline attention are now reusable authorized context. Future SIA tools must invoke the execution domain boundary with trusted actor/resource scope, explicit capabilities, approval and audit. Attention is factual read-time projection, not generated recommendations or intelligence. Unknown progress/health remains unknown. No Phase04 agent roles, enabled tools or execution paths are seeded; executionEnabled remains false. See EXECUTION_MODEL.md.

## Identity

SIA is the MAXPASE GROUP Virtual CEO. SIA is not a chatbot and must not be implemented as arbitrary database access.

## Phase 01 Boundary

Phase 01 defines identity, context, goals, tools, approvals, permissions, recommendations/actions as future contracts, and auditability.

## Tool Control

SIA tools must declare required permissions, scope, risk, and approval requirements. High-impact actions require explicit approval and must create audit events.

The full intelligence engine belongs to a later phase.

## Phase 02 Business Context

The business graph now has explicit group/company structure, ownership, memberships, brands, products, projects and goals. SIA's future tools should call businessService context queries with a trusted execution actor and the required explicit permissions. They must receive only authorized organization scope, never use an unrestricted graph dump or arbitrary Prisma queries. Unknown ownership, legal data and missing records remain unknown rather than inferred.

Phase 02 changes neither the Phase 01 tool/approval contracts nor the intelligence-engine boundary. Business context semantics are documented in BUSINESS_GRAPH.md.

## Phase 03 Identity and Access

The canonical AIRA role list preserves entry 60, SIA — Virtual CEO, as an AGENT designation. It is never a Person, User or human employee. The existing SiaIdentity remains the shared executive identity. Separate SiaRoleAssignment records bind agent roles and explicit organization scopes. Human authorization ignores agent-role assignments.

SIA access inspection checks active identity/role, explicit scoped capability and an enabled tool with the required permission. GLOBAL capabilities are rejected. Approval requirements remain declared by tool contracts; executionEnabled is always false in this phase. Development seeding assigns no SIA roles or tools. Future tools must retain scoped resources, explicit approvals and transactional audit rather than arbitrary database access.
