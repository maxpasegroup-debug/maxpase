# Career Hub Experience Phase 4: Goals and Earnings

This extends experience phases 1-3, not the original Nice Jobs phase numbering. No new tables, migration, rates, company identities, provider or autonomous SIA authority are introduced.

## Goal and planning source

The canonical Goal holds a typed `NICE_JOBS_30_DAY` metadata snapshot bound to one active readiness-backed assignment and its actual Person/division. The participant explicitly proposes an integer quantity, unit and outcome. A bounded deterministic draft apportions the quantity cumulatively across 10, 20 and 30 days and 30 daily practice/work/evidence/report steps. Quantities are plans, not observed results or guaranteed money. No conversion from a desired monetary target to assumed commissions occurs.

The draft records its provider, optional SIA identity, up to five authorized current task references, optional reviewed published same-job incentive version and definition fingerprint. The immutable canonical finance version remains the rule source; its full definition is not copied into generic goal metadata. Rule display requires financial source access and a matching fingerprint. SIA assistance requires the existing enabled `get_worker_day` contract and human AND agent authorization before bounded source reads in the existing transaction. It grants no write tool. Without configuration/authorization, a clearly labeled standard planning template remains available. No model integration or autonomous execution is enabled.

The start is the UTC proposal instant; each day is an elapsed 24-hour window, not a local calendar/workday. Display shows the approved daily window. Waiting for approval does not silently shift the agreed dates; an expired proposal cannot activate and needs replacement.

## Human approval and changes

Each submission uses the existing OperationalRequest, ControlPoint and SiaApproval. An administrator must configure an ACTIVE same-division, non-project, independent human approval control with required `nicejobs.work.manage` and one matching rule assigned to the participant's actual manager account. The manager also needs scoped resource/goal, workspace/person, approval and control access. Names/designations do not authorize.

A narrowly injected request-preparation context permits an actual participant to prepare/submit only the owned proposal under the prevalidated control using `nicejobs.workspace.self`; no roles or general request/control permissions are granted. Notification and resource reads reauthorize ownership. Generic approval routes invoke the same goal binding/fingerprint/current-manager guard. Generic request editing and execution goal editing/progress cannot rewrite controlled career plans; generic goal creation cannot forge their metadata kind.

The manager decides through canonical approvals, then explicitly activates the approved plan after current human authority is rechecked. A material change creates a separate goal snapshot and new approval; activation atomically archives the previous approved goal. Rejection/pending approval leaves the original target unchanged. One active controlled goal per participant/division is enforced at activation. Canonical audit/event references are the approved planning rule and provenance; unapproved drafts are clearly labeled.

## Skills and responsibilities, never money gates

Skill levels project the existing immutable training-plan stages in order. Required activities need canonical completion, or APPROVED evidence when human review is required. Later stages cannot skip an incomplete required level; optional stages do not fabricate unlocks. Expected outcomes remain curriculum practice milestones, not certificates or inferred professional competence.

An unlocked level only makes a new responsibility eligible for manager review. The assigned authorized manager explicitly creates an evidence-required canonical Task under an approved active goal. Task metadata records the goal/request, immutable training-plan ID/fingerprint, stage and progress IDs, with transactional manager audit. Task/goal/onboarding permissions and current approval remain mandatory. No role, access right, salary, wage, wallet eligibility, debit or payment gate is derived from a level. Existing task-assignment workflows remain available; this is an additional skill-backed path, not a universal restriction on all work.

## Earnings source of truth

The existing finance service remains exclusive monetary authority. Optional goal incentive selection requires current financial self access; manager approval/activation of a linked rule requires policy read and a currently applicable reviewed published rule. Worker projections suppress rule details if financial access is revoked. Goal approval never approves an earning, changes a rate, calculates a payable amount or writes a wallet.

Existing independent policy review/publication, closed performance evidence, earning approval, explicit posting and append-only ledger sources continue unchanged. Today and Wallet distinguish verified posted balance, unposted pending incentives, review reservations, available posted funds and payout reservations. Posted balance is not gross lifetime earnings; corrections and settlement debits are included. Transferred remains unavailable, not zero or PAID, because no payout provider exists. Wallet historical self reads remain independent of training and active-work planning.

## Integrity and UI

All goal commands use confirmed strict inputs, session-derived actors, actor-bound idempotency fingerprints, scoped current authorization and transactional canonical audit. Proposal, request/approval and target replacement failures roll back; no database reset, seed or migration is performed. Skill-backed task creation and its approval-source audit share the same transaction.

Today and Work expose outcomes, daily actions, checkpoint drafts, skills and approval history. Existing worker-detail exposes manager review, activation and skill-backed assignment. The seven-section navigation and portal/corporate session isolation remain unchanged. Wallet uses existing ledger/evidence/statement drill-downs and finance controls.

Reads are bounded: latest 25 proposals, 25 controls/policies, training schema limits, 30 daily rows per proposal and three Today wallets. Goal metadata filtering reuses canonical storage; per-proposal authorization/approval reads are bounded but not a high-volume index/search design. The preview is not production load acceptance. Real business targets, training curricula, assigned managers, scoped capabilities and independently reviewed incentive terms still require configuration.
