# Nice Jobs company admission events

The existing Nice Jobs referral link sends an opaque `ref` token to the approved HTTPS destination. Startup Skool persists a referral snapshot on its `ExecutiveRecord` application, including participant, company, opportunity version, referral and capture time. The destination must retain that snapshot with the permanent application. Returning through another route does not replace an earlier attribution.

## Signed delivery

An authorized integration manager creates a company source draft. A different human approves it after configuring `NICEJOBS_SOURCE_BINDING_<connection ID>` as `<company ID>:<secret variable name>` and the secret variable named by `env:<NAME>` (at least 32 random characters). Secrets are private environment configuration, never stored in the connection or sent through the UI. A signed source POSTs to `/api/nicejobs/events/<connection ID>` with headers `x-nicejobs-timestamp` (Unix seconds) and `x-nicejobs-signature` (lowercase SHA-256 HMAC hex of `<timestamp>.<raw body>`). The timestamp must be within five minutes. Payloads are capped at 16 KiB. Retrying the same `eventId` and identical body is safe; changing the body under the same ID is rejected.

The JSON object must contain `eventId`, `companyId`, `opportunityId`, `type`, and ISO UTC `occurredAt`. It may contain `participantId`, `referralToken`, `externalApplicationId`, and `externalAdmissionId`. Application events require `externalApplicationId`. Admission and payment events require `externalAdmissionId`. Payment and refund events require unique `externalTransactionId`, positive decimal `amountMinor`, and three-letter `currency`. Types are `APPLICATION_CREATED`, `APPLICATION_UPDATED`, `ADMISSION_APPROVED`, `PAYMENT_RECEIVED`, `PAYMENT_REFUNDED`, and `ADMISSION_CANCELLED`. The occurrence date may be up to 90 days from receipt; older items require human reconciliation.

The receiver records an **unverified** receipt with immutable event ID, body fingerprint, company scope, attribution and transaction reference. A separate authorized reviewer must verify or reject evidence. Unmatched events remain unmatched until an authorized human supplies the original referral and evidence. A signed event is never proof of payment by itself. Verified payment and refund receipts contribute to net qualifying payment only when linked to a separately verified admission and an approved opportunity payment threshold. Duplicate transaction recognition is blocked by a company-scoped unique index.

## Manual evidence

Where a company has no webhook, an integration manager can create a `manual` source and obtain independent approval. An authorized reconciliation user submits each event with its original referral token and external evidence reference. A different authorized human reviews it. Manual entries are explicitly marked by the source and cannot use the webhook endpoint. Original external transaction references and refund events are preserved. This path does not create wallet credit or payment authority.

## Capacity and financial boundary

An independent partner opportunity cannot publish without configured admission and participant limits, payment threshold, currency and approval evidence. New applications are blocked when either limit is reached; existing records remain. Confirmed capacity counts only separately verified admissions with sufficient net verified payments and no verified cancellation.

The existing versioned Nice Jobs incentive policy supports an admission bonus rule (fixed amount per qualifying admission plus an additional bonus at configured milestones) and a marginal milestone rule. Both require a published partner opportunity linked to an active programme, approved commercial terms, independently verified admission attribution and net verified payment above the opportunity threshold. Milestone position counts qualifying verified admissions, including those whose earning calculation has not yet been requested, in a stable verification-time and ID order. Admission calculations are stored in the existing immutable earning table with a unique admission source; performance calculations retain their snapshot source. No rule is active merely because it was drafted. Policy review is independent, and each calculated earning requires the existing human financial approval before wallet posting. A refund or cancellation before posting blocks posting. Reconciliation flags a posted admission credit affected by a later refund or cancellation for an authorized adjustment or reversal; it does not silently debit the worker. Payout transfer remains unavailable without a configured provider and separate authority.

`20261106010000_nicejobs_admission_incentives` adds a nullable admission reference and makes the snapshot reference nullable with an exactly-one-source constraint, a unique admission index, a foreign key and an updated calculation immutability trigger function. The existing unique performance period constraint becomes a partial unique index for snapshot-sourced earnings, while admission-sourced earnings use the unique admission reference. It does not rewrite existing performance earnings. The new SQL and database-backed approval, concurrency, refund and reversal path require verification against a dedicated development/staging PostgreSQL database before production use. None of these changes approves a real incentive rate, commercial terms or external payment integration.

Apply the additive source-events and admission-incentives migrations only to a positively identified authorized development or staging PostgreSQL database before attempting database-backed integration tests. The guarded PostgreSQL fixture requires `TEST_DATABASE_URL` for a local database named `maxpase_ci` on localhost with `?schema=public`, `MAXPASE_CI_DATABASE_CONFIRMED=true`, and a non-production `NODE_ENV`. Keep credentials private. Never use the Railway production database as a test target.
