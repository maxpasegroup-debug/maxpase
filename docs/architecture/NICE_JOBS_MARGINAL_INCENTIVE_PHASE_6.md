# Nice Jobs Phase 6: marginal incentive foundation

The existing `NiceJobsIncentivePolicy` and immutable `NiceJobsIncentiveVersion` remain the only finance policy system. A new `MARGINAL_MILESTONE` rule can be entered as a scoped draft in the Boss financial policy builder and previewed without persistence or money movement. The preview uses exact integer minor units. For tier `t`, the rate is base plus `(t - 1)` fixed increments, or base multiplied by `1 + (t - 1) * percent / 100`, with the policy rounding mode. A maximum tier can cap the rate. Only admissions in a tier receive that tier's rate; previously earned positions never change. The example 5/6/10 admissions at ₹8,000 with five per milestone and a 50% increase yields ₹40,000/₹52,000/₹1,00,000. These figures are examples, not approved Nice Jobs rates. Existing published, scoped policy versions can be selected as a starting point for a separate job draft; its immutable source version is recorded in the new definition. No existing published policy changes when copied. Marginal drafts themselves cannot yet be published or used as approved base plans.

**Activation gate:** the current performance sources measure leads, tasks, reports and training. None proves that a specific confirmed admission belongs to a worker. The Startup Skool `STARTUP_ADMISSION` record verifies an admission but has no immutable link to a Nice Jobs worker, job, incentive plan or lead. Treating a lead outcome or performance count as a verified admission would create an unauthorized financial claim. Therefore marginal policies may be drafted and previewed, but the server rejects submission for approval and all snapshot based calculations for this rule. No rate or new earning is active. Existing policies and nonmarginal calculations are unaffected.

Before activating a marginal policy, the business must approve written incentive terms, attribution, cancellation/refund treatment, verified issuer/programme and independent approval authority. The software then needs a unique, immutable attribution record connecting the canonical confirmed admission, specific worker assignment, approved job/programme and applicable plan version; independent human verification; replay/rollback protection; and a source specific financial calculation and PostgreSQL safeguard tests. This is also required for a reusable cross-job base template: copying a draft's numbers must never silently change a published version. No such attribution or payable marginal path is claimed in this phase.

Worker financial records now label calculated estimates, pending independent approval, approved but unposted earnings, and posted earnings separately. A posted wallet credit is not evidence of payment; payout delivery remains unconfigured. TARA has no finance write authority.
