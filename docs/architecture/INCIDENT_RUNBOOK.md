# Incident And Failure Handling

1. Protect the boundary: pause traffic or the affected explicit processors using reviewed deployment controls. Do not disable authorization/approval, activate SIA tools or loosen company scope to make failures disappear.
2. Collect correlation ID, safe diagnostic code/timestamp, release identifier and authorized audit/event references. Runtime diagnostics accept fixed codes and generated IDs only, not raw exception/SQL/payload/session/credential values. ORM raw-error logging is disabled; normal server-action failures keep controlled user messages. Infrastructure/service-manager exception logs still require restricted access and reviewed redaction.
3. Investigate with currently authorized domain views: request/approval history, failed operations, message UNKNOWN/SENDING/FAILED, integration receipts, finite job failures and SIA runs. Do not dump unrelated company data or copy private context into incident tickets. Audit visibility itself is scoped and not unrestricted source access.
4. For suspected session compromise, revoke relevant server sessions and rotate the deployment signing key deliberately. For provider compromise, disable the integration through authorized services, rotate external secret plus deployment binding, verify contracts and revalidate consent/policy before reactivation. No credential is written to business/audit records.
5. For uncertain delivery, never reset UNKNOWN/SENDING or retry after restore based on elapsed time. Only a real configured adapter/provider lookup and human-authorized reconciliation can establish the external effect. Definite retryable failures remain bounded and idempotent.
6. For database corruption, failed migration or lost audit storage, stop writes and use the verified snapshot/restore procedure. Audit failure must fail the mutation, not be suppressed. Failed logout revocation/audit leaves the cookie/session uncleared and raises failure; do not claim sign-out succeeded.
7. For abuse/rate saturation, inspect safe counters and apply trusted edge limits. Login account/global budgets and anonymous webhook budgets can be exhausted; app rate limits alone are not DDoS availability controls. Database failures fail closed.
8. Recover only after confirming current identity/capability/scope and human approval/confirmation. Document actual impact, affected authorized resources, recovery evidence and release-owner decision. Independent full-system audit remains separate.

Monitoring foundation: liveness/readiness HTTP, canonical audits/events, real failed-message/job/operation views and structured safe failure IDs. External log collection, alert routing, disk/CPU/database-lock monitoring, backup freshness checks and incident paging are deployment requirements, not configured integrations. No telemetry stack or live-provider health probe is claimed.
